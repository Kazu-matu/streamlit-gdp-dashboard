## 1. データ準備 — 入口はExcelでOK

「うちはDBがない」は理由になりません。手元のExcelファイルや、機器から出力されるCSVファイルがあれば、今日からデータ分析を始められます。

データの準備はAIがサポートします。「このExcelを読み込んで、欠損値を確認して前処理して」と伝えるだけで、AIがpandasのコードを生成します。

> [!NOTE]
> **EUCデータ分析の本質は「ELT（抽出・読込・変換）」への転換**
> 従来の実務では、分析の前に手作業でExcelの行をコピー＆ペーストしたり、不要な列を削除したり、日付書式を書き換えたりする「手動でのデータ加工（前処理）」が行われていました。これは属人化とミスの原因となり、再現性がありません。
> 本フレームワークでは、**「生データをそのままPythonに読み込み（Extract & Load）、コードで一括変換（Transform）する」というELTの設計思想**を推奨します。元ファイルを直接編集せず、加工プロセスをすべてPythonコードとして記録（AIに記述させる）することで、データソースが追加・更新されてもボタン一つで再実行可能になります。


| データソース | Pythonでの読み込み方 | 活用例 |
|---|---|---|
| 🗄️ Oracle / PostgreSQL | `oracledb` / `SQLAlchemy` で接続 | 生産管理DB・販売管理DBの基幹データ活用 |
| 📊 Excel / CSV | `pd.read_excel()` / `pd.read_csv()` | 実験データ・検査記録・生産実績（今日から） |
| 🌐 Web API / IoT | `requests` ライブラリで取得 | 気象データ・IoTセンサーのリアルタイム値 |
| 📄 PDF / テキスト | `pdfplumber` / `pypdf` で抽出 | 検査報告書・仕様書のテキスト化・構造化 |

> **AIへの伝え方（例）**
> 「この実験データのExcelを読み込んで、処理条件ごとに品質指標を比較するグラフを作って」
> → AIが `read_excel`・`groupby`・グラフのコードを一気に生成します。

> [!TIP]
> **大容量データ（100MB以上）の処理について**
> データサイズが非常に大きい場合（目安としてファイルサイズが100MBを超える場合など）、通常の `pandas` でのCSV/Excel読み込みは動作が低速になったりメモリ不足を引き起こす原因となります。
> そのような場合は、以下の高速なライブラリやデータフォーマットを組み合わせて使用することをお勧めします。AIに「データ量が大きいので、〇〇を使って処理コードを書いて」と指示してください。
> - **Polars** (`import polars as pl`): `pandas` に代わる超高速なデータフレームライブラリ。マルチスレッド並列処理により、大容量データを高速に処理します。
> - **DuckDB** (`import duckdb`): CSVやParquetファイルに対して直接インメモリSQLを実行できるカラムナー（列指向）データベース。省メモリかつ超高速に動作します。
> - **Parquet（パーケット）フォーマット**: テキストであるCSVの代わりに、圧縮効率と読み込み速度が極めて高い列指向バイナリ形式の Parquet（`.parquet`）ファイルを使用することで、ディスクサイズ削減とパース速度の大幅向上（数倍〜数十倍）が期待できます。

## 3. 実験計画法

「何をどの順序で実験すべきか」をAIとPythonが設計。実験コストを最小化しながら最適条件を探索します。

| 手法 | 特徴・適した場面 | ライブラリ |
|---|---|---|
| 直交表・田口メソッド | 多因子実験を最小回数で設計。主効果・交互作用を分析。パルプ蒸解条件最適化に実績。 | pyDOE2 |
| 応答曲面法（RSM） | 中心複合計画・Box-Behnken計画で非線形な最適点を探索。3因子で最高品質になる組み合わせを特定。 | statsmodels |
| ベイズ最適化 | 実験結果を学習しながら次の実験点を自動提案。試行回数が少なくても最適解に収束。 | optuna |

### 具体例：パルプ製造の蒸解条件最適化

- **因子**：蒸解温度（160〜180℃）、薬液濃度（14〜18%）、蒸解時間（60〜90分）
- **目的**：カッパー価を目標範囲に保ちながら収率を最大化
- **結果**：直交表L9で9回の実験で最適条件を特定。従来の一因子ずつ変化させる方法より実験回数を **70%削減**。

## 4. 品質管理

手書き・手計算だった品質管理をPythonで自動化。最新データが入ったら管理図が自動更新されます。

| 管理手法 | 内容・自動化できること | AIへの指示・具体例 |
|---|---|---|
| シューハート管理図（X̄-R図・X̄-S図） | CSVを読み込んで管理限界線（UCL・LCL）を自動計算・描画。ネルソン則違反を自動検出してアラート表示。 | 「品質データのCSVでX̄-R管理図を作って。ルール違反の点は赤くして」→ 管理限界を自動計算、Plotlyで生成。違反点を赤マーク。 |
| 工程能力指数（Cp・Cpk） | 規格上下限と実測データからCp・Cpkを自動算出。ヒストグラム＋正規分布曲線で工程の実力を一目で把握。 | 製紙工場の坪量管理：毎時計測CSVを読み込み → X̄-R図を自動更新 → 管理外れをTeamsに自動通知。 |
| CUSUM・EWMA管理図 | 微小な工程シフトを早期検知。シューハート管理図では見逃しやすいトレンドをリアルタイムで監視。 | 品質異常の発見が平均 **2時間** 早まった実績。 |

管理図はStreamlitで社内公開すると、品質部門が毎朝URLを開くだけで最新の工程状況を確認できます。更新はデータを差し替えるだけで自動反映されます。

## 5. 数理最適化

「コスト最小」「生産量最大」「納期厳守」など複数の条件が絡み合う問題を数式として解きます。

> **メタファー：囲碁の「最善手」を瞬時に計算する**
> ベテランの調達担当が「原料Aをどこからどれだけ買うか」を経験で決めているとき、その判断の裏には複数の制約（コスト・納期・品質・在庫）が絡み合っています。数理最適化はその全パターンをコンピュータが計算し、「この配分が数学的に最善」という答えを出します。

| 手法 | 特徴 | ライブラリ |
|---|---|---|
| 線形計画法（LP） | 目的関数・制約条件が線形の問題。原料配合・生産量配分・コスト最小化。最も実績が多い手法。 | PuLP / scipy |
| 混合整数計画法（MIP） | 「整数でなければならない」制約を扱う。スケジューリング・設備選定・配送ルート。 | OR-Tools |
| メタヒューリスティクス | 遺伝的アルゴリズム・焼きなまし法。厳密解が難しい大規模問題に適用。 | DEAP / optuna |

### 製造業での最適化事例 3選

| 課題・分野 | 決定変数 | 目的関数 | 主な制約 | ライブラリ |
|---|---|---|---|---|
| 原料配合最適化 | 原料A〜Fの配合比率 | 原料コスト最小化 | 白色度≥85、強度≥指定値 | PuLP / CVXPY |
| 配送ルート最適化（VRP） | 各車両の訪問順序 | 総走行距離最小化 | 積載量上限、配送時間窓 | OR-Tools / networkx |
| 生産スケジューリング | 製品×設備の割り付け | 段取り時間最小化 | 納期、設備稼働時間 | OR-Tools CP-SAT |

**AIへの指示例**

```
[原料配合最適化]
YOU : 原料A〜Fのコストと品質特性がこのExcelにある。白色度85以上・
      強度指定値以上の制約でコスト最小の配合比を出して
 AI : PuLP で線形計画問題を定式化して解きます。最適配合比と
      達成コストを表とグラフで表示。

[生産スケジューリング最適化]
YOU : 受注一覧のExcelと設備の段取り時間表がある。納期遵守率を
      最大にする生産順序を計算して、ガントチャートで見せて
 AI : OR-Tools CP-SATソルバーでスケジューリング問題を定式化。
      PlotlyのGanttチャートで結果を可視化。
```

最適化の結果はExcelやCSVにエクスポートして既存の業務フローに組み込めます。PuLPで解いた原料配合比をExcelに書き出し、発注担当者がそのまま使う運用が典型例です。

## 6. 機械学習

「データから規則を自動で見つける」— 分類・予測・クラスタリング・異常値検知の4種で製造現場の課題を解きます。

| カテゴリ | サブタイトル | 製造業での活用例 | アルゴリズム |
|---|---|---|---|
| ① 分類 | 「これは何か」を自動判定 | 外観検査の良品/不良品自動判定、設備状態の正常/要注意/要停機分類、不採算品目の自動ラベリング | 決定木 / ランダムフォレスト / SVM |
| ② 予測（回帰） | 「次に何が起きるか」を数値化 | 需要予測・在庫最適化、設備余命予測（RUL）、営業利益の期末着地予測 | Prophet / XGBoost / SARIMA |
| ③ クラスタリング | 「隠れたグループ」を自動発見 | 顧客・品目のセグメンテーション、工程異常パターンの自動検出、類似バッチの自動グルーピング | K-Means / DBSCAN / 階層型 |
| ④ 異常値検知 | 「いつもと違う」を自動で検出 | 設備センサーデータによる異常予兆検知、製品検査時の外れ値検出、稼働ログからの突発異常の早期発見 | Isolation Forest / One-Class SVM / Local Outlier Factor (LOF) |

機械学習モデルの精度向上には大量のデータと試行錯誤が必要ですが、AIがコードを生成するため「まず動かしてみる」ハードルが大幅に下がりました。まずPoCやMVP（最小限のプロダクト）の単位で小さく検証を回し、効果が確認できたらデータを増やして精度を高める進め方が現実的です。

> [!TIP]
> **バイブコーディングによる機械学習・異常値検知アプリの構築コツ**
> 1. **しきい値の動的コントロール**: 異常値検知では「どこからが異常か」の線引き（しきい値パラメータや Isolation Forest の `contamination`）の調整が極めて重要です。AIに「しきい値をStreamlitのスライダーで変更できるようにして、異常点（赤色）がグラフ上でどう変化するかリアルタイムに可視化して」と指示し、現場感覚とデータ特性が一致するしきい値を探索しましょう。
> 2. **特徴量作成（データ変換）もAIに丸投げ**: 機械学習の精度を分ける「特徴量作成」もコードを書く必要はありません。「反応温度と圧力を掛け合わせた指標を追加して精度が上がるか試して」「直近3分間の移動平均値と標準偏差を追加して」など、現場の物理的な仮説を言葉にするだけで、AIが高度な特徴量エンジニアリングのコードを一瞬で生成します。

## 10. セキュリティ前提条件

利用前に必ず確認してください。

- **pip-audit でライブラリの脆弱性チェック** — 使用前に `pip-audit` を実行して `No vulnerabilities` を確認
- **静的コード解析による脆弱性スキャン** — 静的脆弱性検査ツール（`Bandit` など）を利用して、コードにセキュリティ上の問題や脆弱性が内在していないか検証する
- **機密情報を含めない** — 個人情報・未公開営業情報・社外秘技術はコードやデータに含めない
- **認証情報をコードに直書きしない** — パスワード・APIキーは `os.environ.get()` で環境変数から取得
- **成果物は社内に留める** — GitHub Publicリポジトリへのpush・社外クラウドへのアップロード禁止

## 11. データサイエンティスト＆システム開発専門家からの実践的アドバイス

初学者が製造業の現場でデータ分析や数理最適化を実務適用するにあたり、陥りやすい罠と対策をプロの目線からまとめました。

### 11.1 「相関関係」と「因果関係」を混同しない
- **罠**: Pythonで高い相関（例: 原料の物性値Xと製品強度Yの正の相関）が計算できたため、すぐに「原料Xを増やせば強度が増す」と判断してしまう。
- **対策**: 統計的な相関があるからといって、因果関係があるとは限りません。中間に別の要因（例えば、反応温度の上昇が結果として両方に影響しているなど）が介在している可能性があります。必ず物理的・化学的なプロセス知識と照らし合わせ、AIの分析結果がドメイン知識（現場の常識）と矛盾しないかエンジニアが検証してください。

### 11.2 センサーデータの「異常値（外れ値）」の扱い
- **罠**: データの前処理で、欠損値や外れ値を一律に `dropna()` で削除したり、平均値で埋めたり（`fillna()`）して分析を始めてしまう。
- **対策**: 製造現場のセンサーデータには、「計測ノイズ（単なるチャタリングや通信瞬断）」と「物理的なプロセスの急激な変化（装置のヒーター異常など）」の双方が含まれます。前者を消すのは正しいですが、後者を消すと貴重な異常予兆のサインを失うことになります。前処理のコードを書く前に、「その異常値はどういう現場事象から起きたか」を調査し、AIに「〇〇℃以上の場合はセンサー故障としてスキップし、それ以外は異常工程フラグを立てて」と状況に応じた前処理を指示してください。

### 11.3 モデルの「劣化」を想定する（概念ドリフト）
- **罠**: 機械学習で需要予測や歩留まり予測のモデルを作り、一度高精度な結果が出たため、そのシステムを恒久的に放置して運用する。
- **対策**: 装置の経年摩耗、季節の変化（夏と冬での外気温・湿度の差）、原料ロットの変更などにより、プロセスの性質は徐々に変化します。これを「概念ドリフト（Concept Drift）」と呼び、モデルの精度低下を招きます。システム設計の段階から、定期的に最新データを取り込んで再学習（Retraining）する運用や、モデルの予測誤差が一定値を超えたらアラートを出す仕組みを考慮に入れておきましょう。

### 11.4 ゴミを入れればゴミが出てくる（GIGO: Garbage In, Garbage Out）
- **罠**: 数理最適化ソルバーや予測モデルのアルゴリズムを高度にすれば、汚れたデータや不正確な前提条件からでも正しい結果が得られると期待する。
- **対策**: データサイエンスの世界で最も有名な格言の一つです。入力するデータに誤りがあったり、定式化における制約条件（例: 設備の稼働時間の上限）が現実と乖離していれば、世界で最も優れたAIでも「使い物にならないゴミ」を出力します。アルゴリズムの調整に時間を費やすよりも、「現場の実態に即したデータが取れているか」「制約条件の数値が正しいか」の検証に8割の時間を割くべきです。

### 11.5 Streamlitの適切なユースケースと設計上の限界（DBを用いたMVCアプリ構築の罠）
- **罠**: Pythonで簡単にWeb UIが作れるため、本格的なデータベース連携を伴うマルチユーザー向けの更新・登録システム（MVC/CRUDアプリ）をStreamlitで構築しようとしてしまう。
- **対策**: Streamlitは「データの抽出・加工・可視化・出力」を最小限のコードで素早く構築するダッシュボード用途に特化しています。これは画面操作のたびに「プログラム全体を上から下まで再実行する」という極めて特殊な実行モデルによって成立しています。
  - **MVCアプリに不向きな理由**: 画面変化のたびに毎回コード全体が再走するため、状態保持には `st.session_state` を駆使する必要があります。複雑な画面遷移やデータベースの同時実行制御（トランザクション処理・行ロック）、双方向データバインディングなどを無理に実装しようとすると、状態管理コードが肥大化・スパゲッティ化し、パフォーマンスの低下や意図しないバグ（UI上の値の先祖返りなど）を引き起こします。「できないわけではない」ですが、開発・保守コストが爆発的に高くなります。
  - **正しい使い分け**: 
    - **推奨**: DBやCSVからデータを引いてきて分析し、結果をグラフで確認したりファイルをエクスポートする「一方通行のフロー」。
    - **非推奨**: 多数のユーザーが同時にデータを入力・変更し、厳格なトランザクション管理が必要な基幹・業務システム。これらはDjango/FastAPI（バックエンド）＋Vite/Next.js（フロントエンド）といった標準的なWeb開発スタックで構築するのが適しています。

### 11.6 バイブコーディングを成功させる「AIへの語り方」の極意
- **罠**: Pythonや機械学習のライブラリの構文（コードの書き方）を必死に調べて、AIに「〇〇関数の引数をこうして」と技術的な指示を出そうとしてしまう。
- **対策**: それはAIの仕事です。人間は「ドメイン知識（現場の事実やビジネスルール）」を言語化することに集中してください。
  - **技術を語るな、事実を語れ**: 「`MinMaxScaler` を適用して」と言う代わりに、「データの値の範囲がバラバラだから、0〜1の範囲に揃えて分析して」と目的を語ります。
  - **異常や仮説を語れ**: 「この設備は、温度が80度を超えてから圧力が下がると故障する傾向がある」「この2つの因子は連動しているはず」といった現場の知見や仮説をそのままAIにインプットしてください。AIはそれを特徴量や判定ロジックのコードに自動翻訳します。人間は「仕様の決定と結果の検証」に専念するのが、バイブコーディングの真髄です。
