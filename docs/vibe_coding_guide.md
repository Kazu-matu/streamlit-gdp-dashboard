## 0. バイブコーディングとは？

**バイブコーディング（Vibe Coding）** とは、AI（Claude などの LLM）を"相棒"として使い、  
自分はアイデアと方向性を決めるだけで、実装・修正・検証を AI に任せるプログラミングスタイルです。

```
従来の開発:  アイデア → 仕様書 → 設計 → 実装 → テスト → 完成（数週間〜）
                                  ↑ここで詰まる人が多い

バイブコーディング:  アイデア → AI に話す → 動くものが出てくる → フィードバック → 完成（数時間〜）
```

### バイブコーディングの3原則

| 原則 | 説明 |
|---|---|
| **伝える** | やりたいことを日本語で AI に話す。コードは書かなくていい |
| **試す** | 動かしてみて「ここが違う」「これを追加して」と会話する |
| **信頼する** | 細部は AI に任せ、自分は「何を作るか」に集中する |

### 1.1 必要なツール（3つだけ）

| ツール | 役割 | インストール |
|---|---|---|

### 1.2 プロジェクト初期化

フォルダを作って AI に話しかけるだけで始まります。

```powershell
mkdir my-dashboard
cd my-dashboard
```

あとは Claude Code を開いて、こう話しかけるだけです：

```
streamlit と plotly を使った GDP 比較ダッシュボードを作りたい。
uv でプロジェクトを初期化して。
```

AI が `pyproject.toml` を作り、`uv sync` まで走らせてくれます。

## 2. バイブコーディングの実践：会話例

このガイドの元になった実際の開発会話をもとに、  
「どう話しかけるか」のコツを解説します。

---

### フェーズ1：最初の一歩「まず動かす」

#### ✅ 良い話しかけ方

```
世界銀行の API から GDP データを取得して、
国を選んでグラフで比較できる Streamlit アプリを作って。
日本・アメリカ・中国をデフォルトにして。
```

**ポイント：**
- 「何を見せたいか」を具体的に
- デフォルト値まで伝えると一発で近いものができる
- 技術的な詳細（API のエンドポイント等）は不要。AI が調べる

#### ❌ 避けたい話しかけ方

```
ダッシュボードを作って。
```

→ 抽象的すぎて AI も迷います。「誰が・何を・どう見る」を意識しましょう。

---

### フェーズ2：機能追加「どんどん足す」

動くものができたら、会話で機能を積み重ねます。

```
IMF の GDP 成長率タブも追加して。
データ取得ボタンを押したときだけ API を呼ぶようにして。
```

```
日本の経済指標（鉱工業生産・失業率・CPI・景気動向指数）のタブも追加したい。
使えるAPIと指標を調べて提案して。
```

**ポイント：**
- 一度に大量の要件を伝えるより、**1機能ずつ追加**していく方が品質が高い
- 「調べて提案して」と調査から任せると、API の選定まで AI がやってくれる

---

### フェーズ3：バグ修正「エラーをそのまま貼る」

エラーが出たらエラーメッセージをそのままコピペするだけです。

```
こんなエラーが出た：

ModuleNotFoundError: No module named 'plotly'
Traceback:
  File "app.py", line 31, in <module>
    import plotly.express as px
```

→ AI が原因（仮想環境の問題）を特定して、解決策まで実行してくれます。

```
IMF API から 403 エラーが返ってくる。
```

→ AI が代替 API（World Bank の同一指標）を探して、コードごと書き換えてくれます。

**ポイント：**
- エラーを「恥ずかしい」と思わない。むしろエラーは AI への最高の情報
- 自分でデバッグしようとしない。まず AI に投げる

---

### フェーズ4：品質向上「こだわりを伝える」

```
CSV ダウンロードボタンを各グラフの横に追加して。
Excel で開いたとき文字化けしないようにして。
```

```
app.py が 1000 行を超えた。
保守性・可読性・拡張性を考えてリファクタリングして。
```

**ポイント：**
- 「Excel で文字化けしないように」のような**非機能要件**も日本語で伝えられる
- リファクタリングも「やって」と言えばやってくれる。コードを読む必要すらない

---

### フェーズ5：自動テスト「Playwright で動画まで」

```
Playwright でアプリを自動操作して、デモ動画（WebM）を録画するスクリプトを作って。
世界銀行・IMF のデータ取得からグラフ表示まで8ステップで操作して。
```

→ AI が `demo_playwright.py` を一から生成。  
→ 「デモシナリオを実行して」と言えば実際に動かして検証まで完了。

## 3. 爆速開発を支える3つのコツ

### コツ1：「仕様書を先に」ではなく「動かしながら仕様を決める」

```
# バイブコーディング的な仕様決め
「とりあえず世界銀行の GDP を折れ線グラフで出して」
→ 動いた → 「国を複数選べるようにして」
→ 動いた → 「IMF のタブも欲しい」
→ 動いた → 「日本の指標は FRED から取れる？」
```

完璧な仕様書を書いてから動かすより、**動くものを育てる**方が圧倒的に早い。

---

### コツ2：「何をしたいか」と「なぜしたいか」をセットで伝える

```
# NG：何をするかだけ
「エラーハンドリングを追加して」

# OK：なぜするかも添える
「ネットワークが不安定な環境でも使いたいので、
API エラー時はユーザーに分かりやすいメッセージを表示して」
```

「なぜ」を伝えると、AI が**意図に合った実装**を選んでくれます。

---

### コツ3：AI を「コードを書く人」ではなく「一緒に考える人」として使う

```
# 指示するだけの使い方（もったいない）
「〇〇を実装して」

# 一緒に考える使い方（真のバイブコーディング）
「日本の経済指標を可視化したいんだけど、
どの API が使えそう？ メリット・デメリットを比較して提案して」
```

AI は実装だけでなく、**調査・設計・提案**もできます。

## 5. よくある失敗パターンと対策

### ❌ 失敗1：「自分で直そうとする」

エラーを見てコードをいじり始める → 余計に壊れる → 時間を溶かす

**✅ 対策：** エラーが出たら即 AI に渡す。「直して」の一言でいい。

---

### ❌ 失敗2：「全部一度に頼む」

「世界銀行・IMF・FRED・e-Stat を全部取得して8つの指標を4タブで…」

**✅ 対策：** 1機能ずつ積み上げる。動くものを確認してから次へ。

---

### ❌ 失敗3：「AI の出力を信じすぎる」

API のカテゴリコードが間違っていてもそのままにする  
→ `'DATA_INF' KeyError` で気づく（本プロジェクトでも実際に発生）

**✅ 対策：** 必ず動かして確認する。「デモ実行して検証して」と AI に頼めばいい。

---

### ❌ 失敗4：「ドキュメントを後回しにする」

動いたら満足して何も残さない → 後で何が何だかわからなくなる

**✅ 対策：** 「仕様書を更新して」「報告書を作って」も AI が書いてくれる。面倒がらず頼む。

## 7. AI指示書（AI_INSTRUCTIONS.md）を作る

### なぜ指示書が必要か

AIとの会話は**毎回リセット**されます。  
毎回「このプロジェクトはStreamlitで〜」と説明するのは非効率です。

**AI指示書**とは、プロジェクトの文脈をまとめたMarkdownファイルです。  
会話の冒頭に貼り付けるだけで、AIが即座にプロジェクトを把握した状態で動いてくれます。

```
# 指示書なし
あなた：「エラーが出た」
AI：「どんなアプリですか？技術スタックは？」← 毎回これ

# 指示書あり
あなた：「AI_INSTRUCTIONS.md を読んだうえで、このエラーを直して」
AI：「worldbank.py の_wb_get関数ですね、原因は〜」← 即座に文脈把握
```

---

### AI指示書に書く6つの要素

| 要素 | 内容 | なぜ必要か |
|---|---|---|
| **① プロジェクト概要** | 目的・実行方法・URL | AIがアプリの「何のため」を理解する |
| **② 技術スタック** | 言語・FW・ライブラリ・バージョン | 엉뚱한실装を防ぐ |
| **③ ディレクトリ構成** | 各ファイルの役割コメント付き | どこに何を書くかを統一する |
| **④ アーキテクチャ原則** | 守るべきルール・禁止事項 | 設計の一貫性を保つ |
| **⑤ 外部API仕様** | エンドポイント・認証・注意点 | 同じ失敗を繰り返させない |
| **⑥ 作業依頼テンプレ** | 機能追加・バグ修正の依頼例 | 初心者がAIへの伝え方を学べる |

---

### 指示書テンプレート（コピーして使う）

````markdown
# AI開発指示書 — [プロジェクト名]

## 1. プロジェクト概要
**目的**: [何を作るか・誰が使うか]
**実行方法**: `[起動コマンド]`

## 2. 技術スタック
| 項目 | 技術 |
|---|---|
| 言語 | Python 3.10+ |
| フレームワーク | [Streamlit / FastAPI / etc.] |
| パッケージ管理 | uv |

## 3. ディレクトリ構成
```
project/
├── main.py        # [役割]
├── config.py      # [役割]
├── data/          # [役割]
└── views/         # [役割]
```

## 4. 絶対に守るルール
- [例: config.py 以外に定数を書かない]
- [例: .env をコミットしない]
- [例: uv add でのみパッケージを追加する]

## 5. 外部API・接続先
| API | 用途 | 認証 | 注意点 |
|---|---|---|---|
| [API名] | [用途] | [キー名] | [ハマりやすい点] |

## 6. やってはいけないこと
- [例: app.py にロジックを直書きしない]
- [例: 既存の命名規則を変えない]

## 7. 現在の既知の制約・メモ
- [例: XXX APIは403になるためYYYで代替]
- [例: Windows環境のためPOSIXコマンドは使わない]
````

---

### 使い方（どのAIでも同じ）

```
# ChatGPT / Gemini / Copilot の場合
→ チャット冒頭に AI_INSTRUCTIONS.md の内容をコピペして貼り付ける

# Claude Code の場合
→ プロジェクトルートに置くだけで自動的に読み込まれる（CLAUDE.md として認識）
  ※ファイル名を CLAUDE.md にすると Claude Code が毎回自動で読む

# Cursor / GitHub Copilot の場合
→ .cursorrules や copilot-instructions.md として配置すると自動適用
```

---

### 指示書を育てるタイミング

| タイミング | 追記する内容 |
|---|---|
| APIの落とし穴を踏んだとき | 「注意点」に追記 |
| 同じミスをAIが2回したとき | 「やってはいけないこと」に追記 |
| 新しいモジュールを追加したとき | 「ディレクトリ構成」を更新 |
| 設計判断をしたとき | 「アーキテクチャ原則」に理由とともに追記 |

> 指示書は**生き物**です。プロジェクトとともに育てていくことで、  
> AIが「初日から最終日まで同じ文脈で動いてくれる相棒」になります。

## 8. 報告書・ドキュメント作成プロンプト集

バイブコーディングでは実装だけでなく、**ドキュメントも AI に任せる**のが鉄則です。

```

```

## 9. プロジェクト初期開発プロンプト例

### プロンプト1: 世界銀行データ — 各国のGDP比較ダッシュボード
