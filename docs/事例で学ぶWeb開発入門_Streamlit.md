# バイブコーディングで爆速ダッシュボード開発ガイド

> 「アイデアを思いついた瞬間から、動くアプリが手元に。」

対象者：Python 初心者 / バイブコーディング未経験者
難易度：初級
完成まで：**1日以内**

---

## 0. バイブコーディングとは？

**バイブコーディング（Vibe Coding）** とは、AI（Claude などの LLM）を"相棒"として使い、
自分はアイデアと方向性を決めるだけで、実装・修正・検証を AI に任せるプログラミングスタイルです。

```text
従来の開発:
  アイデア → 仕様書 → 設計 → 実装 → テスト → 完成（数週間〜）
                        ↑ ここで詰まる人が多い

バイブコーディング:
  アイデア → AI に話す → 動くものが出てくる → フィードバック → 完成（数時間〜）
```

### バイブコーディングの3原則

| 原則 | 説明 |
|---|---|
| **伝える** | やりたいことを日本語で AI に話す。コードは書かなくていい |
| **試す** | 動かしてみて「ここが違う」「これを追加して」と会話する |
| **記録する** | 決めたこと・ハマったことをドキュメントに残す。AI との会話はリセットされるため |

> **なぜ「信頼する」ではなく「記録する」が3原則に？**
> AI の出力は常に正しいとは限りません。「動かして確認する」「決定事項を残す」習慣が、
> バイブコーディングを安全で再現可能なものにします。

## 1. 開発環境を整える（15分）

### 1-1. 必要なツール（3つだけ）

| ツール | 役割 | インストール |
|---|---|---|
| **Python 3.10+** | プログラムの実行環境 | python.org からインストール |
| **uv** | パッケージ管理（pip の超高速版） | `pip install uv` |
| **copilot** | AI 相棒（バイブコーディングの核心） | VS Code 拡張 or CLI |

### 1-2. プロジェクト初期化

フォルダを作って AI に話しかけるだけで始まります。

```powershell
mkdir my-dashboard
cd my-dashboard
```

あとは Claude Code を開いて、こう話しかけるだけです：

```text
streamlit と plotly を使った GDP 比較ダッシュボードを作りたい。
uv でプロジェクトを初期化して。
```

AI が `pyproject.toml` を作り、`uv sync` まで走らせてくれます。

### 1-3. 最初にやること：指示書と git を準備する

プロジェクトを始める前に、**この2つを必ず先にやる**ことを強くすすめます。

#### git の初期化と .gitignore の確認

```bash
git init
git add .gitignore pyproject.toml .env.example
git commit -m "chore: initial project setup"
```

> **なぜ最初にコミット？**
> AI と一緒に作業していると、気づいたら大量のファイルが変わっています。
> 作業前にコミットしておくと、「元に戻したい」ときに `git reset --hard` で一発で戻せます。

#### .env.example と .gitignore を必ず確認

```bash
# .gitignore に必ず含まれていること
.env          ← API キーが入るファイル（絶対にコミットしない）
__pycache__/
.venv/
*.pyc
```

```text
# AI に確認させるプロンプト
.gitignore に .env が含まれているか確認して。
含まれていなければ追加して。
```

## 2. 指示書（AI_INSTRUCTIONS.md）を最初に作る

バイブコーディングで最も重要なのに、最も見落とされがちなのが **指示書** です。

### なぜ指示書が必要か

AI との会話は**毎回リセット**されます。
毎回「このプロジェクトは Streamlit で〜」と説明するのは非効率です。

```text
# 指示書なし
あなた：「エラーが出た」
AI：「どんなアプリですか？技術スタックは？」  ← 毎回これ

# 指示書あり
あなた：「AI_INSTRUCTIONS.md を読んだうえで、このエラーを直して」
AI：「data/worldbank.py の fetch 関数ですね、原因は timeout 未設定です。修正します。」
       ← 即座に文脈把握
```

### 指示書に書く7つの要素

| 要素 | 内容 | なぜ必要か |
| --- | --- | --- |
| **① プロジェクト概要** | 目的・実行方法・URL | AI がアプリの「何のため」を理解する |
| **② 技術スタック** | 言語・FW・ライブラリ・バージョン | 意図しない技術の追加を防ぐ |
| **③ ディレクトリ構成** | 各ファイルの役割コメント付き | どこに何を書くかを統一する |
| **④ アーキテクチャ原則** | 守るべきルール・禁止事項 | 設計の一貫性を保つ |
| **⑤ 外部API仕様** | エンドポイント・認証・注意点 | 同じ失敗を繰り返させない |
| **⑥ やってはいけないこと** | 禁止事項のリスト | AI が悪手を繰り返すのを防ぐ |
| **⑦ 既知の制約・メモ** | ハマりやすい点・代替手段 | 調査済みの知識を引き継ぐ |

### 指示書テンプレート（コピーして使う）

````markdown
# AI開発指示書 — [プロジェクト名]

## 1. プロジェクト概要
**目的**: [何を作るか・誰が使うか]
**実行方法**: `uv run streamlit run app.py`
**アクセス先**: `http://localhost:8501`

## 2. 技術スタック（変更禁止）
| 項目 | 技術 | バージョン |
|---|---|---|
| 言語 | Python | 3.10+ |
| フレームワーク | Streamlit | 1.40+ |
| チャート | Plotly | 5.20+ |
| データ処理 | pandas | 2.0+ |
| HTTP | requests | 2.31+ |
| パッケージ管理 | uv | - |

## 3. ディレクトリ構成
```text
project/
├── app.py        # タブ配置・全体の組み立てのみ
├── config.py     # 定数・デフォルト値のみ
├── data/         # API 呼び出し・DataFrame を返すだけ（st.* 禁止）
└── views/        # Streamlit 描画のみ（API 呼び出し禁止）
```

## 4. 絶対に守るルール
- `data/` では `st.*` を一切使わない
- `@st.cache_data(ttl=...)` をすべての fetch 関数につける
- fetch 関数の引数は tuple のみ（list は UnhashableTypeError になる）
- エラー時は必ず空の `pd.DataFrame()` を返す（None は返さない）
- `.env` は絶対にコミットしない
- uv 以外のパッケージ管理ツールは使わない

## 5. 外部API・接続先
| API | 用途 | 認証 | 注意点 |
|---|---|---|---|
| World Bank | GDP データ | 不要 | レートリミットあり。`ttl=86400` でキャッシュ |
| IMF Datamapper | 成長率 | 不要 | 403 エラー多発 → World Bank の NY.GDP.MKTP.KD.ZG で代替 |
| FRED | 米経済指標 | FRED_API_KEY | `.env` に保存 |

## 6. やってはいけないこと
- `app.py` にデータ取得ロジックを直書きしない
- `requests.get()` に `timeout=` をつけ忘れない
- `st.error(str(e))` でスタックトレースをそのままユーザーに見せない
- `st.set_page_config()` を `setup_page()` 以外から呼ばない

## 7. 現在の既知の制約・メモ
- IMF Datamapper は 403 になるため World Bank 代替を使用中
- Windows 環境のため POSIX コマンドは使わない（PowerShell を使う）
- e-Stat API は ESTAT_APP_ID が必要（.env に設定済み）
````

### 指示書を育てるタイミング

| タイミング | 追記する内容 |
|---|---|
| API の落とし穴を踏んだとき | 「注意点」に追記 |
| 同じミスを AI が2回したとき | 「やってはいけないこと」に追記 |
| 新しいモジュールを追加したとき | 「ディレクトリ構成」を更新 |
| 設計の判断をしたとき | 「アーキテクチャ原則」に理由とともに追記 |

> 指示書は**生き物**です。プロジェクトとともに育てることで、
> AI が「初日から最終日まで同じ文脈で動く相棒」になります。

### 各 AI ツールへの読み込ませ方

```text
Claude Code  → CLAUDE.md としてルートに置くと自動読み込み
Cursor       → .cursorrules として配置
GitHub Copilot → .github/copilot-instructions.md として配置
ChatGPT / Gemini → チャット冒頭にファイル内容をコピペ
```

## 3. バイブコーディングの実践：会話例

このガイドの元になった実際の開発会話をもとに、
「どう話しかけるか」のコツを解説します。

### フェーズ1：最初の一歩「まず動かす」

#### 良い話しかけ方

```text
世界銀行の API から GDP データを取得して、
国を選んでグラフで比較できる Streamlit アプリを作って。
日本・アメリカ・中国をデフォルトにして。
```

**ポイント:**

- 「何を見せたいか」を具体的に
- デフォルト値まで伝えると一発で近いものができる
- 技術的な詳細（API のエンドポイント等）は不要。AI が調べる

#### 避けたい話しかけ方

```text
ダッシュボードを作って。
```

抽象的すぎて AI も迷います。「誰が・何を・どう見る」を意識しましょう。

---

### フェーズ2：機能追加「どんどん足す」

動くものができたら、会話で機能を積み重ねます。

```text
IMF の GDP 成長率タブも追加して。
データ取得ボタンを押したときだけ API を呼ぶようにして。
```

```text
日本の経済指標（鉱工業生産・失業率・CPI・景気動向指数）のタブも追加したい。
使えるAPIと指標を調べて提案して。
```

> **大きな変更の前に必ず git コミット**
>
> 新しいタブ・モジュールの追加など、複数ファイルが変わる作業の前には必ずセーブポイントを作ります。
>
> ```bash
> git add app.py views/worldbank_tab.py
> git commit -m "feat: add WorldBank tab"
> ```
>
> こうすることで「新しいタブを追加したら既存のタブが壊れた」ときに、すぐ元に戻せます。

**ポイント:**

- 一度に大量の要件を伝えるより、**1機能ずつ追加**していく方が品質が高い
- 「調べて提案して」と調査から任せると、API の選定まで AI がやってくれる

---

### フェーズ3：バグ修正「エラーをそのまま貼る」

エラーが出たらエラーメッセージをそのままコピペするだけです。

```text
こんなエラーが出た：

ModuleNotFoundError: No module named 'plotly'
Traceback:
  File "app.py", line 31, in <module>
    import plotly.express as px
```

AI が原因（仮想環境の問題）を特定して、解決策まで実行してくれます。

```text
IMF API から 403 エラーが返ってくる。
```

AI が代替 API（World Bank の同一指標）を探して、コードごと書き換えてくれます。

**ポイント:**

- エラーを「恥ずかしい」と思わない。むしろエラーは AI への最高の情報
- 自分でデバッグしようとしない。まず AI に投げる
- 解決後は **指示書の「既知の制約」に残す**（同じトラブルを繰り返さないため）

---

### フェーズ4：品質向上「こだわりを伝える」

```text
CSV ダウンロードボタンを各グラフの横に追加して。
Excel で開いたとき文字化けしないようにして。
```

```text
app.py が 1000 行を超えた。
保守性・可読性・拡張性を考えてリファクタリングして。
```

> **リファクタリング前のセーブポイント**
>
> リファクタリングはファイル数が大きく変わる作業です。必ず作業前にコミットしてください。
>
> ```bash
> git add .
> git commit -m "chore: checkpoint before refactor — app.py 1014 lines"
> ```

**ポイント:**

- 「Excel で文字化けしないように」のような**非機能要件**も日本語で伝えられる
- リファクタリングも「やって」と言えばやってくれる

---

### フェーズ5：自動テスト「Playwright で動画まで」

```text
Playwright でアプリを自動操作して、デモ動画（WebM）を録画するスクリプトを作って。
世界銀行・IMF のデータ取得からグラフ表示まで8ステップで操作して。
```

AI が `demo_playwright.py` を一から生成。
「デモシナリオを実行して」と言えば実際に動かして検証まで完了します。

## 4. ドキュメントを作る（バイブコーディングの完成条件）

> **「動けば完成」ではありません。**
> ドキュメントが揃って初めて、情報部門へのデプロイ依頼や引き継ぎができます。

### 4つの必須ドキュメント

プロジェクトの `docs/` フォルダに以下の4ファイルを作ります。
テンプレートが `docs/テンプレート_01_要件定義.md` 〜 `テンプレート_04_報告書.md` にあります。

| ファイル | 作るタイミング | 内容 |
|---|---|---|
| `docs/01_要件定義.md` | コードを書く前 | 何を作るか・誰が使うか・機能一覧 |
| `docs/02_仕様書.md` | 設計が固まったとき | データソース・画面・API 仕様・処理フロー |
| `docs/03_テスト仕様書.md` | テストを書く前 | テスト方針・テストケース一覧 |
| `docs/04_報告書.md` | テストが通ったとき | テスト結果・不具合・デプロイ依頼書 |

### ドキュメントを適時更新するルール

AI はコードを変更するたびにドキュメントの更新を促します。
自分でも以下のタイミングで更新する習慣をつけましょう。

| このとき | このドキュメントを更新 |
|---|---|
| 新しいデータソース（API）を追加 | `02_仕様書.md` のデータソース一覧 |
| 新しいタブ・グラフを追加 | `02_仕様書.md` の画面仕様 |
| 新しい設定値・API キーを追加 | `02_仕様書.md` + `.env.example` |
| テストを追加・変更 | `03_テスト仕様書.md` |
| テストを実行した | `04_報告書.md` のテスト結果欄に記録 |
| バグを修正した | `04_報告書.md` の不具合一覧に記録 |

### ドキュメント作成プロンプト集

#### 仕様書の作成・更新

```text
このアプリの仕様書を docs/02_仕様書.md に作成して。

以下のセクション構成で：
1. システム概要（タブ一覧・データソース）
2. 技術スタック（表形式）
3. ファイル構成（ディレクトリツリー）
4. データソース仕様（エンドポイント・パラメータ・レスポンス形式）
5. 画面仕様（サイドバー・メイン画面の説明）
6. 処理フロー（ユーザー操作 → データ取得 → 描画 の流れ）
7. エラーハンドリング一覧
8. 環境設定（.env のキー一覧）
```

#### テスト仕様書の作成

```text
テスト仕様書を docs/03_テスト仕様書.md に作成して。

以下を含めて：
- テスト方針（何をどこまでテストするか）
- E2E テストケース一覧（操作手順・期待結果）
- テスト実行コマンド
```

#### 完了報告書の作成

```text
プロジェクト完了報告書を docs/04_報告書.md に作成して。

以下を含めて：
- プロジェクト概要（目的・開発期間・担当者）
- 成果物一覧（ファイル・機能・ドキュメント）
- テスト結果（実行コマンド・結果の貼り付け）
- 不具合一覧（発見したバグと対応）
- 既知の制限事項
- 本番環境へのデプロイ依頼書（情報システム部門向け）
```

#### セキュリティ検査 + 報告書への追記

```text
以下のセキュリティ検査を実行して、結果を docs/04_報告書.md に追記して。

1. 依存パッケージの脆弱性スキャン（uv run pip-audit）
2. ソースコードの静的解析（uv run bandit -r app.py config.py data/ views/）

報告書には検出件数・重要度・総評を表形式で追記して。
```

#### アーキテクチャ図の更新

```text
docs/02_仕様書.md のシステム構成セクションを現状に合わせて更新して。
Mermaid で以下を記載して：

1. モジュール関係図（graph TD）
   - app.py / config.py / data 層 / views 層 / 外部APIの依存関係
2. データ取得フロー（sequenceDiagram）
   - ユーザー操作 → キャッシュ確認 → API 呼び出し → 描画
```

## 5. 爆速開発を支える3つのコツ

### コツ1：「仕様書を先に」ではなく「動かしながら仕様を決める」

```text
バイブコーディング的な仕様決め:
「とりあえず世界銀行の GDP を折れ線グラフで出して」
→ 動いた → 「国を複数選べるようにして」
→ 動いた → 「IMF のタブも欲しい」
→ 動いた → 「日本の指標は FRED から取れる？」
```

完璧な仕様書を書いてから動かすより、**動くものを育てる**方が圧倒的に早い。
ただし、動くたびに仕様書も少しずつ更新していくことで、後から書き直す手間をなくします。

---

### コツ2：「何をしたいか」と「なぜしたいか」をセットで伝える

```text
# NG：何をするかだけ
「エラーハンドリングを追加して」

# OK：なぜするかも添える
「ネットワークが不安定な環境でも使いたいので、
API エラー時はユーザーに分かりやすい日本語のメッセージを表示して。
スタックトレースは画面に出さないで。」
```

「なぜ」を伝えると、AI が**意図に合った実装**を選んでくれます。

---

### コツ3：AI を「コードを書く人」ではなく「一緒に考える人」として使う

```text
# 指示するだけの使い方（もったいない）
「〇〇を実装して」

# 一緒に考える使い方（真のバイブコーディング）
「日本の経済指標を可視化したいんだけど、
どの API が使えそう？ 無料・登録不要・更新頻度の観点でメリット・デメリットを比較して提案して」
```

AI は実装だけでなく、**調査・設計・提案**もできます。

## 7. よくある失敗パターンと対策

### 失敗1：「自分で直そうとする」

エラーを見てコードをいじり始める → 余計に壊れる → 時間を溶かす

**対策:** エラーが出たら即 AI に渡す。「直して」の一言でいい。
解決後は指示書の「既知の制約」に追記して次回に備える。

---

### 失敗2：「全部一度に頼む」

「世界銀行・IMF・FRED・e-Stat を全部取得して8つの指標を4タブで…」

**対策:** 1機能ずつ積み上げる。動くものを確認してから次へ。
各機能完成後に git コミットしてセーブポイントを作る。

---

### 失敗3：「AI の出力を確認しない」

API のカテゴリコードが間違っていてもそのままにする
→ `'DATA_INF' KeyError` で気づく（本プロジェクトでも実際に発生）

**対策:** 必ず動かして確認する。「デモ実行して検証して」と AI に頼めばいい。
AI の出力はゴールの**ドラフト**として扱い、動作確認で品質を保証する。

---

### 失敗4：「ドキュメントを後回しにする」

動いたら満足して何も残さない → 後で何が何だかわからなくなる

**対策:** 「仕様書を更新して」「報告書を作って」も AI が書いてくれる。
機能を1つ追加するたびに、対応するドキュメントを更新する習慣をつける。

---

### 失敗5：「大きな変更前に git コミットを忘れる」

リファクタリング途中でコードが壊れた → 元に戻せない → 全部書き直し

**対策:** 2ファイル以上が変わる作業の前には必ず git コミット。
AI に依頼する前にこう確認する：

```text
この変更の前に、現在の状態を git commit しておきたい。
変更されるファイルを教えて。
```

---

### 失敗6：「API キーをソースコードに書いてしまう」

うっかり `config.py` に `API_KEY = "sk-xxxxx"` と書いてコミット
→ GitHub に公開 → キーが漏洩

**対策:** API キーは必ず `.env` ファイルに書く。
ソースコードには `os.environ.get("FRED_API_KEY")` のみ書く。
AI に依頼するときも「API キーは .env から読むようにして」と明示する。

---

## 8. 開発テンプレート：話しかけるだけで始まるダッシュボード

以下をそのまま AI に貼り付けるとダッシュボードの骨格が作れます。

```text
以下の条件で Streamlit ダッシュボードを作って。
copilot-instructions.md のルールに従って実装して。

【概要】
（例：世界各国の XXX を比較するダッシュボード）

【データソース】
（例：World Bank API / FRED / e-Stat）

【表示したいもの】
- タブ1：（例：XXX の推移グラフ）
- タブ2：（例：XXX の比較）

【操作】
- 対象を選択できる
- 期間を指定できる
- ボタンを押したときだけ API を叩く

【その他】
- CSV ダウンロードボタンをつける
- uv で環境管理
- エラーは日本語で表示
- API キーは .env から読む
```

## 9. ステップアップのロードマップ

```text
Step 1: このガイドを読んで1つ動くものを作る（今日）
    ↓
Step 2: 自分のデータ（CSV・API・スプレッドシート）を読み込んでみる
    ↓
Step 3: 「なぜこのコードになるのか」を AI に説明させて読む
    ↓
Step 4: リファクタリングを頼んで、変更前後の構造の違いを学ぶ
    ↓
Step 5: 指示書・仕様書・報告書を自分で書けるようになる
    ↓
Step 6: 自分で少し変更できるようになる（ここで初めて自分でコードを書く）
```

バイブコーディングは「コードを書かない」ではなく、
**「動くものから学ぶ」** という新しい学習スタイルです。

---

## 10. まとめ

| バイブコーディングでできること |
|---|
| アイデアを日本語で話すだけでアプリが動く |
| エラーをそのまま渡すだけで修正される |
| 「調べて提案して」で API 選定から任せられる |
| リファクタリング・テスト・ドキュメントも全部頼める |
| セキュリティ検査まで一緒に完走できる |

| バイブコーディングで守ること |
|---|
| 大きな変更前には必ず git commit する |
| API キーは .env に書く。絶対にコミットしない |
| 指示書（AI_INSTRUCTIONS.md）を育てていく |
| 4つのドキュメントを機能追加のたびに更新する |
| AI の出力は必ず動かして確認する |

> **「コードが書けないからアプリが作れない」時代は終わった。**
> **アイデアと、記録する習慣があれば、今日から作れる。**

### プロンプト1：世界銀行データ — 各国のGDP比較ダッシュボード

```text
あなたは優秀なシニア Python エンジニアです。
以下の要件に従って、世界銀行のデータを利用した各国 GDP 比較ダッシュボードを Streamlit で作成してください。

# 成果物の出力手順（厳守）
1. 仕様書（Markdown）: アプリの目的・システム構成・画面設計・機能要件をまとめたドキュメント
2. アプリケーションコード: 仕様書に基づいた Python コード

# 技術スタック（厳守）
- 言語: Python 3.10+
- フレームワーク: Streamlit
- データ取得: requests, pandas
- 可視化: Plotly
- パッケージ管理: uv（pyproject.toml で管理）

# 機能要件
1. データ取得
   - 世界銀行 API から GDP（現在の米ドル建て）/ 指標コード: NY.GDP.MKTP.CD を取得する
   - @st.cache_data(ttl=86400) でキャッシュする
   - timeout=10 を必ず設定する
   - エラー時は空の DataFrame を返す（raise しない）
2. UI レイアウト
   - サイドバー: 国のマルチセレクト（日・米・中・独・印をデフォルト）、期間スライダー、取得ボタン
   - メイン画面: Plotly 折れ線グラフ、データ表（エクスパンダー内）、CSV ダウンロードボタン
3. アーキテクチャ
   - data/ と views/ に責務を分離する
   - views/ で st.* を使う。data/ では st.* を使わない
   - エラーメッセージは日本語で st.warning() を使う

# 自己レビュー（出力前）
- data/ に st.* 呼び出しがないか？
- すべての fetch 関数に @st.cache_data があるか？
- timeout= が設定されているか？
```
